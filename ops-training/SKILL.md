# 运维实训加速器

## 概述

公司实训大纲就是路线图。AI 不帮你规划学什么——帮你快速做通、记牢、能应付上机考核。

**核心原则**：做中学，产出即沉淀。不是先学再做，而是做着学着，做完东西自然留下。

## 加载后自动推进

加载后检查 `ai/wiki/training-progress.md`：
- 不存在 → 等待用户发第一个实训任务
- 存在 → 读取进度，报出："当前进度：X/Y 已完成。最近在做 {当前项}。下一个实训发过来就开始。"

## 3 步循环

用户发实训任务（如"实训一 nginx"）→ 进入循环：

### Step 1：理解任务

1. 一句话说清：这个实训要掌握什么
2. 列验收标准：怎么算做完了（不是"配完了"，而是"能访问/能复现/能通过考核"）
3. 涉及多个独立组件时拆成 2-3 个子任务

**输出**：任务理解 + 验收标准，让用户确认。

### Step 2：做通 + 记录

逐个子任务执行。每做完一个：

1. **做通**：最小可行步骤搭起来，看到效果
2. **记录**：写到 `ai/wiki/{技术名}/` 下，三个文件：

```
ai/wiki/{技术名}/
├── setup.md           # 从零搭建的完整步骤（能复现）
├── commands.md        # 常用命令 + 一句话说明（只记实际用到的）
└── troubleshooting.md # 踩过的坑 + 解决方法
```

**记录原则**：
- 只记实际用到的，不记"可能有用"的
- 踩坑记录比官方文档更有价值
- 每条命令写清楚"这行在干什么"

**卡住时**：自查 5 分钟 → 问 AI（给完整上下文，包括错误日志和环境信息）→ 还不行换思路。解决后第一时间写入 troubleshooting.md。

### Step 3：自检

实训做完后 AI 出 2-3 道快问快答题：
- 通过 → 标记完成，更新 `training-progress.md`
- 卡住 → 标为薄弱点，下次实训前先花 5 分钟补

## 进度追踪

维护 `ai/wiki/training-progress.md`：

```markdown
## 实训进度

- [x] 基础环境搭建 (2024-xx-xx)
- [x] Docker 基础操作
- [ ] PostgreSQL 主库搭建 ← 当前

## 薄弱点
- pg WAL 机制还没完全搞懂
```

## 运维铁律

1. **先跑通再理解**：搭起来看到效果 → 回头看架构 → 故意搞破坏练排障
2. **AI 出配置，你读懂**：AI 可以生成配置，但你必须能解释每行为什么要有
3. **卡住 5 分钟就问**：自查 → 问 AI（给完整上下文）→ 不行换思路
4. **排障是最好的学习**：出问题先猜根因在哪 → 查日志/配置/网络 → 解决后复盘"根因是什么、怎么预防"

## 与 learn-by-doing / ops-learning 的关系

| | learn-by-doing | ops-learning | ops-training |
|---|---|---|---|
| 场景 | 自学新技术 | 深入学运维 | 快速过公司实训 |
| 谁定内容 | AI 引导用户定 | AI 引导用户定 | 公司实训大纲 |
| 阶段 | 7 | 6 | 3 |
| 工作区 | 6+ 文件 | 4 文档 | 3 文件 + 进度 |
| 检验 | 费曼检验 | 费曼+自检 | 快问快答 |

三者可以叠加：实训用 ops-training 快速过，遇到想深入的技术用 ops-learning 补，自学新领域用 learn-by-doing。

## 禁止事项

- 不要让用户先看完文档/视频再动手
- 不要让用户背诵命令、参数、默认值
- 不要直接给故障答案（引导排查思路）
- 不要一次给太多信息（保持每步 30 分钟内可完成）
- 不要在用户没发实训任务时主动规划"你应该学什么"
