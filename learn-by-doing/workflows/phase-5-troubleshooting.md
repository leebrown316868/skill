# Phase 5：排障练习 + 场景题

## 触发条件

费曼检验通过后，进入排障阶段。

## 两类题目的区分

Phase 5 包含两类题型，考察不同维度的能力：

| 维度 | 排障题（Drill） | 场景题（Scenario） |
|------|----------------|---------------------|
| **考察** | 动手排查能力 | 理解深度 + 判断力 |
| **形式** | 给日志/现象，用户查 | 给场景描述，用户分析 |
| **答案** | 具体根因 + 修复命令 | 判断结果 + 设计理由 |
| **来源** | Phase 4 之后的薄弱点 | 跨模块综合理解 |
| **难度层级** | Drill 1→2→3 | 无层级，按模块组合 |

**场景题示例（不同于排障题）：**
- "服务从单机迁移到 K8s 集群后偶发超时，可能是哪些原因？列出排查优先级。"
- "Nginx 前面加 CDN 后，你的日志里客户端 IP 全变成 CDN 节点 IP，怎么修复？对原有功能有什么副作用？"
- "用户要求支持 10000 并发，你当前的 nginx + gunicorn 架构哪里会成为瓶颈？"

**排障题见下面三层 Drill。**

## 场景题设计规则

- 基于 LEARNING_MAP.md 中 **已完成且费曼检验通过** 的模块
- 至少关联 2 个模块（跨模块综合）
- 不要有唯一正确答案 — 考察排查优先级排序和取舍理由
- 用户答完后 AI 追问"如果你的方案有 X 限制，备选方案是什么？"

## 三层 Drill

### Drill 1：Simulated（模拟排障）

AI 给出日志或配置片段，用户仅凭证据诊断。

```
AI: "这个 nginx 返回 502，日志是 [xxx]，可能是什么问题？"
用户: "检查 upstream 是否在运行"
AI: "对。你应该看什么命令？"
```

**适用场景：**
- 用户没有真实环境可用
- 作为 Drill 2 的前置练习
- 快速覆盖多种故障模式

### Drill 2：Guided real environment（引导式真实环境）

用户在自己的真实环境中排查，AI 只给安全的检查命令。

```
AI: "你的应用返回 500。在不改任何配置的情况下，先检查什么？"
用户: "看日志？"
AI: "对，运行 X 命令看看最近的错误日志。"

安全规则：
- AI 只推荐只读命令（cat / tail / grep / curl / describe / get）
- AI 不推荐可能导致数据损坏或服务中断的命令
- 用户要执行任何写入操作前，AI 必须解释影响并要求确认
```

### Drill 3：AI-native controlled（AI 原生受控排查）

允许使用 AI 生成假设、检查命令和修复候选；学习者保留问题定义、检查顺序、安全决策和证据判断权。

```
AI: "用户反馈登录偶尔失败。你自己去查。"
用户: [定义影响范围 → 收集证据 → 让 AI 提出多个假设 → 选择检查顺序
      → 验证根因 → 审查修复 → 回归验证]
AI: [评判对错，记录薄弱点]

学习者必须能够说明：
- 为什么优先检查当前假设
- 哪条证据支持或否定根因
- 修复有什么副作用
- 哪个回归证据表明问题确已解决
```

可选做 3~5 分钟无生成式 AI 的口头控制检查，但不要求脱离 AI 重做排障。

## 流程

```
用户完成 Phase 4
  ↓
AI 基于 LEARNING_MAP.md 和 ai/wiki/ 设计排障题
  ↓
按 Drill 1 → 2 → 3 梯度出题；Drill 3 允许 AI 协作但要求完整证据链
  ↓
用户诊断
  ↓
AI 评判 + 记录：
  ├── 排对了 → 写入 troubleshooting.md
  └── 做错了/漏了 → 写入 learning-record (weak-spot)
```

## 排障题设计规则

- 每次只出一个故障场景
- 故障场景必须基于用户学过的模块
- 不要用"记忆类"故障（"这个参数默认值是多少"）
- 要用"理解类"故障（"为什么连不上"）
- 排障题与场景题交替出，不要连出多道同类型

## 退出条件

- [ ] 核心故障场景能在 AI 协作下受控排查，且能解释假设、证据和修复风险（Drill 3 通过）
- [ ] troubleshooting.md 已记录排查过程
- [ ] 薄弱点已标记到 learning-records 和 LEARNING_STATE.md
