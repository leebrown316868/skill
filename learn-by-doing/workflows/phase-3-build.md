# Phase 3：拆任务 + 动手干

## 触发条件

Phase 2 完成。

## 教学辅助规则

> 引用 `SKILL.md` §教学原则。Phase 3 是用户最密集接收新知识的阶段，必须遵守以下规则。

### 三层次教学法（每条 todo 必用）

当 AI 提供 just-in-time 帮助时，**不允许只给命令/配置**。必须按顺序覆盖：

1. **背景概念**：为什么需要这个命令/配置？不用它会怎样？它解决什么场景？
2. **参数/配置含义**：核心参数的作用（不列全部），每行配置/每个 flag 解释设计理由
3. **边界与坑**：这个配置在什么情况下会失效？常见误用是什么？

**判断标准**：用户拿到帮助后能回答"为什么这样写"才算合格。只会复制粘贴 = AI 教法不合格。

### 场景题穿插节奏

完成以下里程碑时，出一道场景题检验理解深度：

| 时机 | 场景题类型 | 时长 |
|------|-----------|------|
| 每 2-3 条 todo 完成后 | 概念对比 / 容量场景 | 3-5 min |
| 每个模块完成后 | 设计场景 / 故障场景 | 5-10 min |
| 卡住后解决时 | "如果条件变了还会怎么挂？" | 2-3 min |

场景题不等同于 Phase 5 排障题 — 这里考察的是"理不理解为什么"，不是"能不能修好"。

## 流程

### 1. 拆任务为 TO_DO.md

按 `formats/templates.md` 中 TO_DO.md 格式拆分：

- 每条 todo ≤ 30 分钟
- 每条必须有验收命令和预期结果
- 每条必须关联一个 ai/wiki/ 条目
- 标注依赖关系（prerequisites）
- 确保覆盖 MISSION.md 中的所有验收标准

### 2. 逐条执行

```
做一条 todo
  ↓ 用户动手（AI 提供 just-in-time 帮助）
  │   └── AI 检查：帮助内容是否覆盖了三层次（背景→参数→边界）？
  ↓ 做通了
  ↓ 运行验收命令 → 确认结果匹配预期
  ↓ 更新 ai/wiki/{topic}/xxx.md（关键命令、配置、验证方法、踩坑记录）
  │   └── ai/wiki 条目中也需要体现"为什么这样写"的设计理由，不只是命令列表
  ↓ 更新 LEARNING_MAP.md → 对应模块打 [x]
  ↓ 运行短费曼检验（见 Phase 4 简化版）
  ↓ 检查是否需要出场景题（2-3 条 todo 后 / 模块完成后）
  ↓ 更新 LEARNING_STATE.md
  ↓ 更新 REVIEW_QUEUE.md（如适用）
  → 下一条
```

### 3. 卡住时

```
用户卡住
  ├── 先自己查 5 分钟（带着问题查文档/搜索）
  ├── 再来问 AI → 提供完整上下文：
  │   - 想做什么
  │   - 试了什么
  │   - 看到了什么错误
  │   - 在哪个模块/todo
  └── 解决了 → 把踩坑过程写进 troubleshooting.md + ai/wiki/
```

### 4. 完成一个模块后

运行完整费曼检验（Phase 4）→ 写入 learning-record

- [ ] ai/wiki/ 已更新对应条目
- [ ] 核心模块的费曼检验已通过
