# AI 时代学习 - 实践示例

> 这些示例展示了如何在具体场景中应用「学分类不学实例」的四步回答框架。

---

## 示例 1：理解项目结构（为什么拆文件）

### 学习者问题
"为什么需要 validators.py 和 exceptions.py？不能都放在 commands.py 里吗？"

### 四步回答

**第一步：直接回答**
```
可以放一起，但分开更好。因为这三样东西的"变化原因"不同：
- 验证逻辑会因为业务规则变
- 异常类型会因为错误场景变
- 命令逻辑会因为功能需求变

变化原因不同的东西，就该分开。
```

**第二步：模式识别**
```
这是「关注点分离」模式 — 你在别处也见过：
- 厨房里刀具、调料、锅具分开放（使用场景不同）
- 公司里人事、财务、技术分部门（专业领域不同）
- 代码里 model、service、controller 分层（职责不同）

本质问题：一个东西会因为多个原因改变吗？会 → 拆开。
```

**第三步：权衡分析**
```python
# 放在一起（什么情况下可以接受？）
def add_expense(amount, category):
    class ValidationError(Exception): pass
    if category not in DEFAULT_CATEGORIES: ...
    if amount <= 0: ...
    ...

# 可以接受的场景：项目只有 1 个文件、只有你自己用、不会扩展
# 不能接受的场景：多人协作、项目会增长、需要单独测试
```

**第四步：判断标准**
```
下次遇到"要不要拆文件"的问题，问自己：
1. 这个逻辑会被多个地方用吗？  → 是 → 独立文件
2. 这个逻辑需要单独测试吗？    → 是 → 独立文件
3. 这个逻辑会因为不同原因变化吗？→ 是 → 独立文件

三个都是"否" → 放一起也没问题，不要过度拆分。
```

## 示例 2：理解技术选型（Decimal vs float）

### 学习者问题
"为什么用 Decimal 不是 float？"

### 四步回答

**第一步：直接回答**
```
float 有精度误差，金额算错了会出大问题。Decimal 没有这个误差。
→ 0.1 + 0.2 在 float 里等于 0.30000000000000004
→ 在 Decimal 里等于精确的 0.3
```

**第二步：模式识别**
```
这是「精度与性能的取舍」模式：
- float 快但不精确 → 适合科学计算（允许误差）
- Decimal 精确但慢 → 适合金额计算（不允许误差）

类似模式：
- SQLite vs PostgreSQL：轻量 vs 功能完整
- JSON vs Protocol Buffers：可读 vs 性能
- 列表 vs 集合：有序 vs 去重

判断标准永远是：你的场景最在意什么？
```

**第三步：权衡分析**
```
选 Decimal 的代价：
- 计算速度慢 3-10 倍
- 语法稍复杂（要用字符串初始化）
- 不能直接和 float 混算

但在金额场景下，这些代价完全可以接受。
速度差异在财务系统中几乎感知不到。
```

**第四步：判断标准**
```
选择依据：这个数据允许有误差吗？
- 不允许（金额、库存、计数）→ Decimal / int
- 允许（物理模拟、统计、ML）→ float
```

## 示例 3：理解设计模式（装饰器）

### 学习者问题
"@field_validator 是什么？"

### 四步回答

**第一步：直接回答**
```
装饰器 = 给函数"加装功能"的语法糖。

@field_validator('category')
def validate_category(cls, v): ...

等价于：validate_category = field_validator('category')(validate_category)

你不需要手写装饰器。你只需要能读懂它，知道它在干什么。
```

**第二步：模式识别**
```
这是「中间件/拦截器」模式 — 在不修改原函数的情况下，插入额外逻辑。

你在别处见过：
- Flask 的 @app.route    → 给函数"注册为路由"
- pytest 的 @pytest.fixture → 给函数"注册为测试夹具"
- Python 的 @staticmethod  → 给方法"去掉 self 参数"

本质：声明式编程 — 用标记代替调用。
```

**第三步：权衡分析**
```
不用装饰器（手写调用）：
validator_registry.register('category', validate_category)
validate_category(value)

用装饰器：
@field_validator('category')
def validate_category(cls, v): ...

装饰器的优势：声明式、可读性高、Python 惯用法
装饰器的劣势：执行顺序不直观、调试稍难
```

**第四步：判断标准**
```
你的学习优先级：
必学 ✅ 知道装饰器是什么、能读懂带装饰器的代码
    ✅ 能判断 AI 生成的装饰器用法对不对
不用学 ❌ 手写自定义装饰器（AI 能生成）
       ❌ 装饰器执行顺序的细节（用到再查）
```

## 示例 4：AI 辅助开发流程（做新功能）

### 场景：学习者要做订单功能

```
❌ 旧方法（先学再做）
1. 查 Pydantic 文档，记住所有参数
2. 手写 Order 模型
3. 手写验证逻辑
4. 自己调试错误
→ 学习者花了 2 小时学文档，还没开始做功能

✅ 新方法（做中学）
1. 确认需求理解
   "订单需要哪些字段？哪些必填？哪些验证？"
   → 能描述给 AI 就够了

2. 让 AI 生成
   "用 Pydantic 写一个订单模型，包含金额、商品、数量，
    金额必须正数，数量必须大于 0"

3. Review 代码（这是真正学习的地方）
   - 金额用了 Decimal 吗？ ✅
   - 验证逻辑对吗？ ✅
   - 有边界问题吗？ ❌ 数量可以是小数吗？应该限制为整数

4. 让 AI 修正 + 理解为什么
   "数量应该是整数，不能是小数"
   → 理解：为什么要限制类型？因为业务语义。

5. 自检
   - 我能描述给 AI 让它生成类似的模型吗？ ✅
   - 我能判断 AI 写的对不对吗？ ✅
   - 我能换一个场景复用吗？（比如商品模型） ✅
```

## 示例 5：调试思维（数据流定位法）

### 场景：RAG 系统回答质量差

```
❌ 低效方法
"回答质量差，怎么办？" → 盲目改参数 → 不知道改了什么

✅ 数据流定位法
"数据在哪一步出了问题？让我们追踪一下："

Step 1: 文档分块
  → chunk_size 多大？overlap 多大？
  → 抽样看 3 个 chunk，内容合理吗？

Step 2: 向量检索
  → 用户问题 embedding 后，top-5 检索结果相关吗？
  → 如果不相关 → 分块或 embedding 的问题
  → 如果相关但没被排到前面 → 检索参数的问题

Step 3: 生成回答
  → 传给 LLM 的 prompt 包含了什么上下文？
  → LLM 是否被正确引导使用检索结果？

判断标准：
- 分块不合理 → 调 chunk_size / overlap / 分块策略
- 检索不准 → 加 Rerank / 换 embedding 模型
- 生成不好 → 调 prompt / 换模型
```

## 学习笔记模板

引导学习者用这个结构记录每个新概念：

```markdown
## [概念名称]

### 一句话定义
[什么是什么]

### 解决了什么问题
[没有它会怎样]

### 属于什么模式
[分类到已有的模式树上]

### 数据怎么流的
[输入 → 处理 → 输出]

### 判断标准
[什么时候用它，什么时候不用]

### 常见误区
[AI 容易在这里犯错 / 初学者容易搞混]
```

**要点**：笔记里不记"语法怎么写"，只记"为什么这样设计"和"怎么判断"。
