# ops-triage：陌生系统运维认知提取

## 用途

面对一个没接触过的生产系统，按 **发现事实 → 建立关系 → 验证假设 → 沉淀模板** 的循环，把原始输出提炼成可迁移的运维认知。

不是让 AI 替你查服务器——是你带着 AI 按框架排查，你来读结论、建模、验证。

## 步骤概览

```
Phase 0: 定目标 → 这次要掌握什么能力？
Phase 1: 探索   → 采集机器事实
Phase 2: 建模   → 把事实连成关系
Phase 3: 验证   → 确认模型在真实世界成立
Phase 4: 沉淀   → 写入上下文包 + 文档
```

---

## Phase 0：定目标

### 做什么

开始查之前，先写清楚这一轮的目标。目标是**能力**，不是清单。

### 写法

```
❌ 差："了解 PostgreSQL"
✅ 好："掌握 PG 的部署方式、备份恢复链路、主从关系——能回答"如果 PG 挂了怎么恢复""

❌ 差："看一遍目录结构"
✅ 好："能画出这台机器上的数据流——请求从哪进、数据存哪、日志去哪"
```

### 完成标准

目标写好后反问自己：

> "这个目标完成后，我能做什么现在做不到的事？"

答不出来就重写。

---

## Phase 1：探索 (Discovery)

### 做什么

按目标跑命令收集事实。**不做判断，只贴原始输出。**

### 要点

- 让 AI 按目标出命令，你来执行
- 每跑完一条，你只看"输出是否正常"，不做深度解读
- 产出是**原始事实清单**，不是结论

### 分层的命令参考

这个命令列表是参考——AI 会根据你的目标选出具体的命令。详见 [`commands.md`](commands.md)。

### 完成标准

```
□ 当前层级的所有相关命令已执行
□ 原始输出已收集，未跳过任何异常（如报错、空目录、权限拒绝）
□ 确认：你清楚"我查了什么，看到了什么"
```

---

## Phase 2：建模 (Modeling)

### 做什么

把孤立事实连成关系。**这是产生理解的步骤，也是最容易被跳过的。**

### 怎么做

用一段话或一个箭头图，画出：

```
什么组件 → 产生什么数据 → 流向哪里 → 被谁消费
```

### 例子

```
事实池：
  - wal_clean.sh 删1天前的WAL
  - /data/lib/postgres/wal_log/ 有WAL归档
  - /root/.ssh/known_hosts 有139的记录

模型：
  PG (pg-uc)
    ↓ 产生WAL
  wal_log/
    ↓ rsync 主动拉取
  139备份机
    ↓
  恢复机 ← 全量备份 + WAL

问题浮现：
  139是谁？恢复流程验证过吗？
```

### 完成标准

```
□ 每个孤立的发现都连到了一条链路上
□ 你能用自己的话讲出"XX怎么工作的"
□ 标记出了模型中"不确定"的环节 → 这是 Phase 3 的验证目标
```

---

## Phase 3：验证 (Validation)

### 做什么

确认模型在真实世界成立。有两种验证：

### 3a：横向验证（跨机确认）

去相关的其他机器确认模型中的假设。

例如：

```
模型说"139备份机拉WAL"
→ 登139确认：有 rsync 任务吗？有备份目录吗？有日志吗？
```

### 3b：纵向验证（路径闭环）

走一遍关键路径，确认每一步都有答案。

```
PG挂了怎么恢复？
  停止业务 → 恢复全量备份 → 应用WAL → 启动服务 → 验证数据
  ↑ 每一步有SOP吗？验证过吗？
```

### 完成标准

```
□ 模型中的每个假设在真实机器上有证据支持
□ 关键故障场景的恢复路径至少纸上走过一遍
□ "不确定"的环节要么已确认，要么移入 Unknown
```

---

## Phase 4：沉淀 (Knowledge)

### 做什么

只把**验证通过**的信息写进上下文包。不记 AI 自己能重新发现的东西。

### 上下文包结构

```
项目上下文包/
├── 00-semantic.md      # 语义上下文：缩写、命名、业务映射
│   ← 示例：UC=手麻系统, AAIM=麻醉小程序, aims-mw=中间件库
│   ← 规则：AI 永远推理不出来，必须人给
│
├── 01-topology.md      # 拓扑上下文：机器关系、流量路径
│   ← 示例：138(业务+DB) → 139(Loki) ← 158(备份)
│   ← 规则：跨机信息需要人给出起点
│
├── 02-decision.md      # 决策上下文：架构决策记录
│   ← 示例：为什么应用+数据库同机？→ 厂商交付方案
│   ← 规则：AI 猜不到历史原因，必须人工确认
│
└── 03-unknown.md       # 待确认项
    ← 示例：MongoDB 是否有副本集？
    ← 规则：记录"知道不知道什么"，下一轮入口
```

### 取舍标准

每条信息写进去之前问 3 个问题：

```
1. 下次遇到类似系统能复用吗？
   否 → 不记，用时重查

2. 不知道会导致误操作吗？
   否 → 可选，可记可不记

3. AI 能从机器自动发现吗？
   是 → 不记，AI 下次自己查
   否 → 必须记入上下文包
```

三条"否"才进上下文。

### 完成标准

```
□ 上下文包 00-03 已更新
□ 每一条信息都有"为什么它值得记"的理由
□ Unknown 清单清晰，下一轮可以直接接上
□ 你确认：这些笔记能在 3 个月后帮你恢复这个系统
```

## 通用指南

### 每次自问的三个核心问题

```
1. 这个系统在维护什么？（数据）
2. 这个系统依赖什么？（服务、网络、存储）
3. 这个系统怎么保命？（备份、高可用、恢复）
```

### 执行节奏

```
上午：探索 (Phase 1)     — 跑命令，贴输出，不做笔记
下午：建模+验证 (Phase 2-3) — 连关系，跨机确认，走恢复路径
晚上：沉淀 (Phase 4)     — 更新上下文包，标记 Unknown
```

### 质量检查清单

每个模块完成后：

```
□ 如果这个模块挂了，我知道怎么恢复吗？
□ 系统出问题时，我知道从哪里开始排查吗？
□ 我能讲清楚这个模块的数据流吗？
□ 哪些是 AI 告诉我的，哪些是我自己验证过的？
□ 哪些是这个系统特有的，哪些是通用的？
```

三条以上"不确定"→ 继续。

### 三类信息的处理策略

```
不确定来源  → 处理方法
机器上的    → 查配置 / 试命令 / 看日志
跨机器的    → 登录另一台确认 / 问人
业务含义    → 问同事 / 问厂商 / 看文档
历史原因    → 问老人 / 推演"如果是你会为什么这么选"
```
